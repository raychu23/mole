# T33 team-server — prior art (R0)

Owner mole-builder-9 (a13). Fetched 2026-10-29 via web_search/web_extract. Each entry: approach · who uses it · their reported numbers/claims (dated) · fits T33? · what we borrow.

## 1. GitHub webhook best practices (HMAC verify, ack <10s, X-GitHub-Delivery dedupe)
- Source: GitHub Docs, "Validating webhook deliveries" https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries (current, accessed 2026-10-29); GitHub Docs "Best practices for using webhooks" (cited at https://screenshotneo.com/blog/receive-webhook-events-java, accessed 2026-10-29); Hookdeck "Guide to GitHub Webhooks Features and Best Practices" https://hookdeck.com/webhooks/platforms/tutorial-github-webhooks (accessed 2026-10-29).
- Approach: verify `X-Hub-Signature-256` = `sha256=` + HMAC-SHA256(secret, raw body) using constant-time compare (`crypto.timingSafeEqual`/`hmac.compare_digest`), never a parsed/re-serialized body. GitHub expects a 2xx **within 10 seconds**; anything slower should be moved off the request path into a queue. `X-GitHub-Delivery` is a stable UUID per delivery (same value on a GitHub-initiated redelivery) and is the documented idempotency key; GitHub delivers **at-least-once**, so duplicates are expected and must be absorbed, not treated as errors.
- Who uses it: every GitHub App/webhook consumer (Probot, Zapier, CI providers); it is GitHub's own documented contract, not a vendor opinion.
- Numbers/claims: 10s ack ceiling (GitHub's published timeout); dedupe key = delivery UUID (not event id, not payload hash) per GitHub's own header semantics.
- Fits T33: yes — exactly M25's ack<1s (tighter than GitHub's own 10s) and the 10%-duplicate replay test.
- What we borrow: raw-body HMAC verify with timing-safe compare; dedupe on `X-GitHub-Delivery` with a DB unique constraint (in-memory set is explicitly called out as unsafe for production — we use Postgres); "verify → dedupe → enqueue → 2xx" as the entire webhook handler, everything else in a worker.

## 2. Probot architecture
- Source: probot/probot README "How it works" https://github.com/probot/probot/blob/master/README.md (accessed 2026-10-29); Jason Etcovitch "Build your own Probot" https://jasonet.co/posts/build-your-own-probot (accessed 2026-10-29); Sentry blog "Exception Perceptions: Automate Your Workflow with Probot" (accessed 2026-10-29).
- Approach: thin HTTP layer (webhook verify via `@octokit/webhooks`) emits into an internal EventEmitter; app code registers `app.on("issues.opened", handler)`; a separate auth layer (`@octokit/auth-app`) mints short-lived installation tokens from the GitHub App's JWT, cached per installation; `context.repo()`/`context.octokit` give handlers an authenticated client without touching auth.
- Who uses it: Stale, GitHub/Slack integration, thousands of GitHub Apps; `@octokit/webhooks` is also used standalone by non-Probot apps.
- Numbers/claims: none quantitative (framework claim: eliminates "drudgery" of webhook verification + auth handstands).
- Fits T33: yes — our boundary explicitly says `@octokit/webhooks` for ingest.
- What we borrow: the three-stage shape (verify+route via `@octokit/webhooks` → dispatch by event name → authenticated client per installation), and Probot's choice to keep the webhook verify/dispatch layer separate from business-logic handlers (maps directly onto our ingest→queue split). We do NOT adopt Probot's GitHub App auth itself (non-goal: no real GitHub App registration) — we fake installation auth with a recorded-fixture Octokit-shaped client.

## 3. Backstage catalog ingestion (processors + refresh loop)
- Source: Backstage docs "Custom processors" https://backstage.io/docs/features/software-catalog/external-integrations/processors (accessed 2026-10-29); "External integrations" https://backstage.io/docs/features/software-catalog/external-integrations (accessed 2026-10-29); "The Life of an Entity" https://backstage.io/docs/features/software-catalog/life-of-an-entity (accessed 2026-10-29); "Catalog Configuration" https://backstage.io/docs/features/software-catalog/configuration (accessed 2026-10-29).
- Approach: catalog backend continuously ingests from configured sources into its DB (ingestion), runs processors on a fixed interval over every entity (processing: preProcessEntity → validateEntityKind → postProcessEntity), then "stitches" every processor's contributions into the final entity record consumed by the API. Entity providers push/schedule raw data; processors are pure functions over one entity at a time and must not make slow external calls (would delay the whole loop). Orphaned entities (no longer emitted) are marked, not deleted, until GC.
- Who uses it: Spotify (origin), widely adopted OSS internal-developer-portal (CNCF sandbox project).
- Numbers/claims: default `processingInterval` configurable (example: 45 min); no catalog-specific throughput numbers published.
- Fits T33: yes — our index-rebuild-from-git loop is exactly an ingestion+processing loop over `.mole/` files instead of YAML catalog-info files.
- What we borrow: separate ingestion (webhook → queue job "pull git ref, read `.mole/*`") from processing (parse records → upsert index rows, never delete directly — mark orphaned then GC on next successful full rebuild) from stitching (recursive-CTE views that assemble the final decision graph at read time, not at write time). This directly motivates M25's "index == rebuild from git" check: git stays the entity source, Postgres is a derived, rebuildable cache — same relationship as Backstage's catalog DB to its YAML sources.

## 4. Sourcegraph / zoekt indexing architecture
- Source: sourcegraph/zoekt design doc https://github.com/sourcegraph/zoekt/blob/main/doc/design.md (accessed 2026-10-29); Sourcegraph docs "Sourcegraph architecture" https://sourcegraph.com/docs/admin/architecture (accessed 2026-10-29); Sourcegraph blog "Shard merging" https://sourcegraph.com/blog/tackling-the-long-tail-of-tiny-repos-with-shard-merging (accessed 2026-10-29).
- Approach: trigram posting-list index per shard (one repo → one or more shards, mmap'd files), index built once per branch/commit and rebuilt incrementally; non-indexed "searcher" path covers anything not yet indexed. Index is a derived artifact of the repo's git content — can always be regenerated from source.
- Who uses it: Sourcegraph Cloud/Enterprise, many large orgs (Uber, Reddit per public case studies — not re-verified here).
- Numbers/claims: shard size ≈3.5x corpus size; shard target 100 MiB before flush (design doc, undated-but-current main branch, accessed 2026-10-29).
- Fits T33: partially — T33 does not need trigram search, but the "index is a rebuildable derived artifact of the versioned source, never the source of truth itself" principle is exactly M25's `index == rebuild-from-git` requirement.
- What we borrow: the principle (not the trigram mechanics) — our Postgres index must be byte-for-byte reconstructible by replaying `.mole/` files from git history, so the replay bench can assert equality against a from-scratch rebuild.

## 5. Transactional outbox (Chris Richardson, microservices.io)
- Source: microservices.io "Pattern: Transactional outbox" https://microservices.io/patterns/data/transactional-outbox.html (accessed 2026-10-29); ADR example applying it https://github.com/mohd2sh/CleanArchitecture-DDD-CQRS/blob/main/docs/architectural-decisions/ADR-004-outbox-pattern.md (accessed 2026-10-29).
- Approach: a service command that must both change its own DB state and notify another system cannot use 2PC across a DB and a broker; instead, write the notification into an `outbox` table **in the same DB transaction** as the state change, and have a separate relay process poll/deliver outbox rows to the broker, deleting/marking them only after successful send. Guarantees "notification exists iff the transaction committed" and at-least-once delivery (so notification handlers must be idempotent).
- Who uses it: documented as one of Richardson's core microservices patterns (book "Microservices Patterns", 2018); widely implemented (Debezium CDC-based outbox relays, Spring Integration's JDBC channel store, countless in-house implementations per the collected examples above).
- Numbers/claims: qualitative pattern, no vendor-specific throughput numbers; its own stated tradeoff is eventual consistency (relay polling delay) vs. guaranteed delivery.
- Fits T33: directly — M25 requires "0 lost notifications" under duplicate/shuffled replay, which is precisely what an outbox-with-relay guarantees (the alternative, "publish in-request, then update DB", can silently drop a notification if the process dies in between).
- What we borrow: write every notification (check-run post, question-routing message) to a Postgres `outbox` table in the same transaction as the state change that produced it; a worker polls/claims unsent outbox rows (via pg-boss, see below) and marks them delivered only after the fake-GitHub-API call succeeds; never "fire and forget" a notification mid-transaction.

## 6. Postgres row-level security (RLS) multi-tenant guides
- Source: AWS DB blog "Multi-tenant data isolation with PostgreSQL Row Level Security" https://aws.amazon.com/blogs/database/multi-tenant-data-isolation-with-postgresql-row-level-security (accessed 2026-10-29); thenile.dev "Shipping multi-tenant SaaS using Postgres Row-Level Security" https://thenile.dev/blog/multi-tenant-rls (accessed 2026-10-29); AWS Prescriptive Guidance PDF (accessed 2026-10-29); dev.to "How I Used PostgreSQL Row-Level Security to Isolate 15+ SaaS Tenants" https://dev.to/syedahmedx3/how-i-used-postgresql-row-level-security-to-isolate-15-saas-tenants-2l6f (accessed 2026-10-29).
- Approach: every tenant-owned table carries a `tenant_id`/`org_id` column; `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` + `FORCE ROW LEVEL SECURITY`; policies compare the row's tenant column against a per-connection/session value (`current_setting('app.current_org_id')`, set with `SET LOCAL` inside the request transaction) so filtering happens at the engine, not in app code (an automated `WHERE`, applied even to queries the app forgot to filter). Critical gotchas: superusers and the table **owner** bypass RLS by default unless `FORCE ROW LEVEL SECURITY` is set, so the app must connect as a non-owner role; `SET LOCAL` inside explicit transactions avoids leaking tenant context across pooled connections (PgBouncer transaction mode).
- Who uses it: AWS RDS/Aurora Postgres customers broadly (pool multi-tenancy model); thenile.dev built a dedicated Postgres-compatible service around it; is the AWS Prescriptive Guidance's recommended approach for the "pool" SaaS partitioning model.
- Numbers/claims: RLS overhead "negligible... less than 2 milliseconds per statement" if tenant_id leads every composite index (per datatrenddynamics.com guide, accessed 2026-10-29) — unverified vendor-style blog claim, treated as directional only.
- Fits T33: directly — this is the named approach for M25's leak test ("0 leaked records... user without read access... through API and MCP").
- What we borrow: `org_id` column + RLS policy on every multi-tenant table; app connects as a non-owner `FORCE ROW LEVEL SECURITY` role (never the migration/owner role) in request/job code; set `app.current_org_id` via `SET LOCAL` inside each request's transaction (never a bare connection-level `SET`, to avoid pool leakage); `tenant_id`-leading composite indexes.

## 7. MCP authorization spec (2025-06-18) / OAuth 2.1
- Source: MCP spec "Authorization" https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization (accessed 2026-10-29); MCP tutorial "Understanding Authorization in MCP" https://modelcontextprotocol.io/docs/2025-06-18/tutorials/security/authorization (accessed 2026-10-29); GitHub source of the spec doc https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2025-06-18/basic/authorization.mdx (accessed 2026-10-29).
- Approach: authorization is OPTIONAL but, when used over HTTP-based transports (streamable HTTP, SSE), servers **MUST** implement OAuth 2.0 Protected Resource Metadata (RFC9728) so clients can discover the authorization server; authorization servers **MUST** implement OAuth 2.1 (draft-ietf-oauth-v2-1-13) with PKCE etc.; Dynamic Client Registration (RFC7591) is SHOULD; STDIO-transport servers SHOULD NOT use this flow (env-var credentials instead). Flow: client discovers AS via `/.well-known/oauth-protected-resource` → OAuth2.1 auth-code+PKCE → bearer access token on every MCP request.
- Who uses it: the official TypeScript/Python MCP SDKs ship `requireBearerAuth` middleware and `mcpAuthRouter` helpers implementing exactly this; reference implementations exist in FastMCP (Python) and the TS SDK.
- Numbers/claims: none quantitative; it is a protocol requirement, not a benchmark.
- Fits T33: directly — task requires "remote MCP server... streamable HTTP... OAuth 2.1 auth (2025-06-18 spec)".
- What we borrow: streamable-HTTP MCP server from the official `@modelcontextprotocol/sdk`; bearer-token auth middleware pattern (`requireBearerAuth`) backed by a **local test OAuth issuer** (non-goal explicitly forbids a real OAuth provider) that mints JWTs scoped per org, validated the same way a real AS's tokens would be; tokens carry an org claim that becomes the RLS `app.current_org_id` for that MCP session, so MCP reads/writes get leak protection for free from §6.

## 8. pg-boss (Postgres-backed queue, no Redis) vs alternatives
- Source: pgboss.io "pg-boss" / "Introduction" https://pgboss.io/ , https://pgboss.io/introduction , https://pgboss.io/api/queues (accessed 2026-10-29); timgit/pg-boss GitHub https://github.com/timgit/pg-boss (accessed 2026-10-29); npm page https://www.npmjs.com/package/pg-boss (accessed 2026-10-29).
- Approach: job queue built entirely on Postgres using `SELECT ... FOR UPDATE SKIP LOCKED` so concurrent workers claim jobs without blocking each other, with atomic commit guarantees; jobs can be created **inside the same DB transaction** as the business write that produced them (perfect fit for an outbox-driven relay); supports retries w/ exponential backoff, dead-letter queues, cron scheduling, LISTEN/NOTIFY low-latency wakeup, multi-master (safe to run N Node processes against one DB), and ships OpenTelemetry traces/metrics natively. Requires Node ≥22.12 and Postgres ≥13 — no Redis, no separate broker process.
- Who uses it: teams "that already run PostgreSQL and would rather not add another system to operate" (pg-boss's own positioning); embeddable via PGlite for fully in-process/test use.
- Numbers/claims: no public throughput numbers; architectural claim (SKIP LOCKED-based, no polling-induced lock contention) is Postgres's own documented mechanism, not pg-boss-specific marketing.
- Fits T33: directly named in the task contract ("pg-boss queue (Postgres-backed, no Redis)").
- What we borrow: pg-boss as the queue between webhook-ingest and the rebuild/outbox-relay workers; jobs enqueued in the same transaction as the delivery row insert (so a delivery is queued iff it was durably recorded — this is itself a transactional-outbox application, see §5); dead-letter queue for repeatedly-failing jobs; its built-in OTel instrumentation feeding into our collector (§9). For tests we considered PGlite as an embedded alternative (also pg-boss-compatible) but the task non-goals explicitly offer `pg_ctl`-managed local Postgres, which we use for the real M25 bench since it's closer to production Postgres semantics (RLS, SKIP LOCKED) than PGlite's WASM engine.

## 9. OpenTelemetry semantic conventions for GenAI
- Source: OpenTelemetry semantic-conventions "gen-ai-spans.md" (v1.37.0) https://raw.githubusercontent.com/open-telemetry/semantic-conventions/v1.37.0/docs/gen-ai/gen-ai-spans.md and v1.39.0/v1.41.0 variants (accessed 2026-10-29).
- Approach: standardizes span shape for GenAI operations — span name `{gen_ai.operation.name} {gen_ai.request.model}`, span kind `CLIENT` (model calls over network) or `INTERNAL` (same-process/tool execution), `gen_ai.provider.name` attribute discriminates vendor-specific attribute sets, dedicated `execute_tool {tool.name}` span shape for tool calls (status: development as of the fetched versions).
- Who uses it: adopted into the main OpenTelemetry semantic-conventions registry (not vendor-specific); referenced by Microsoft's own mirror and various GenAI SDK instrumentations.
- Numbers/claims: none quantitative — a naming/shape spec.
- Fits T33: directly — task requires OTel spans "on every request and job" and that any model step sit behind a swappable interface; when (never, per non-goals) a real model call is made the span shape would follow this convention.
- What we borrow: span-per-stage naming discipline (`webhook.ack`, `queue.job <name>`, `index.rebuild`, `check_run.compute`, `mcp.request <tool>`) mirroring the spec's `{operation} {target}` naming pattern; `execute_tool {tool.name}` naming reused verbatim for MCP tool-call spans since MCP tool execution is explicitly in-scope for this convention family.

## 10. MLflow run/experiment format
- Source: mlflow/mlflow docs "tracking.rst" https://github.com/mlflow/mlflow/blob/master/docs/source/tracking.rst (accessed 2026-10-29); mlflow.org "MLflow Tracking" https://mlflow.org/latest/tracking.html and /docs/3.0.1/tracking (accessed 2026-10-29).
- Approach: tracking organized around **runs** (one execution), optionally grouped into **experiments**; each run records code version (git commit), start/end time, source, string **params**, numeric **metrics** (each with a full value history over `step`/`timestamp`), and file **artifacts**; default local backend writes to an `mlruns/` directory structure (`experiment_id/run_id/{params,metrics,tags,meta.yaml}`), usable without a server.
- Who uses it: de-facto standard experiment-tracking format across ML teams; T16 (already integrated in this repo, per `loop_status.py`) already writes `runs.jsonl` lines read back by an MLflow-format parser (`mlflow runs 34/34` in T16's M13 result) — so there is in-repo precedent to reuse rather than reinvent.
- Numbers/claims: none quantitative — a data-model spec.
- Fits T33: directly — task requires "eval runs written in MLflow format"; T16 already established `runs.jsonl` → MLflow-run translation in this repo.
- What we borrow: reuse T16's existing `runs.jsonl` → MLflow run-directory writer/reader rather than building a second one; T33's bench writes `{time, commit, cmd, exit, metrics:{M25:{...}}}` lines exactly like every other task's `runs.jsonl` (R4), and a thin script maps each line to an `mlruns/<exp>/<run_id>/metrics/<key>` file (param = cmd/commit, metrics = the M25 sub-values) so the same MLflow-format viewer built for T16 can read T33's runs without a new reader.

## Net design (what T33 borrows from each, combined)
`@octokit/webhooks`-shaped HMAC verify (§1) → Probot-style dispatch (§2) → delivery row insert + pg-boss job enqueue in one DB transaction (§5 outbox + §8 pg-boss) → worker rebuilds the Postgres index from `.mole/` files read from git at the delivered SHA, Backstage-processor-style (ingest raw → process/validate → stitch via recursive-CTE views) (§3), with git remaining the rebuildable source of truth the way zoekt's shards are a rebuildable derived index of the repo (§4) → every multi-tenant table RLS-scoped by `org_id` with a non-owner, `FORCE ROW LEVEL SECURITY` role and `SET LOCAL app.current_org_id` per request (§6) → check-run results and question-routing messages written to the same outbox table and relayed by a pg-boss worker to the fake GitHub API (§5+§8) → remote MCP server over streamable HTTP, bearer-token OAuth 2.1 per the MCP spec, backed by a local test issuer (§7), whose tokens carry the org claim RLS reads (§6) → every stage emits an OTel span named `{stage} {target}` per the GenAI span-naming convention (§9) → the M25 bench appends to `runs.jsonl` in the same shape every other Mole task uses, readable by T16's existing MLflow-format viewer (§10).
