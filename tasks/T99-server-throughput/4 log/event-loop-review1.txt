## Methodology
A fake `git` placed first on PATH sleeps 300ms then execs the real git with the same argv, so
every `ls-tree`/`show` call the rebuild-index job path makes costs >= 300ms deterministically
(not dependent on machine load or fixture size). 4 orgs x (1 ls-tree + 3 show) = 16 slow calls
per run, fired via `Promise.all` (no bounding across orgs, matching a burst of concurrent
webhook-triggered jobs). A `setInterval` heartbeat (10ms) runs concurrently; the test asserts
`maxHeartbeatGapMs < 150` (half of one call's own 300ms sleep -- wide margin either way).

IMPORTANT FINDING during this work: `perf_hooks.monitorEventLoopDelay` does NOT register delay
from `execFileSync`/`spawnSync` blocking at all on this Node version (v22.21.0), even for an
unmistakable, deliberately huge block -- verified directly, independent of this task's fixtures:
  - `execFileSync('sleep', ['0.3'])` x4 back-to-back (1.2s of real, wall-clock-confirmed
    blocking) -> monitorEventLoopDelay max = 0ms.
  - A plain synchronous `while (Date.now() < until) {}` busy-spin for 1.2s (no subprocess,
    unambiguous single-thread CPU block) -> monitorEventLoopDelay max = 0ms too.
  - The SAME two scenarios measured with a `setInterval` heartbeat instead: max gap ~1269ms
    (sync busy-spin) / ~13ms (async `execFile`) -- correctly discriminates.
This is why the ORIGINAL event-loop.spec.ts's `monitorEventLoopDelay`-based assertion never
failed against the pre-T99 rebuild-index-only scenario either (4 log/red.txt's own earlier
"rebuild-only, 2/6 concurrent orgs: p99 ~5-19ms (pre-T99 sync code)" entries) -- the instrument
itself cannot see this bug class, independent of fixture size or load. Switched to a
`setInterval`-heartbeat-based assertion, which is directly verified to detect it.
